1 — APPLICATION DETAILS
========================================================================

--- What does your application do? ---

Eric is a community management bot for Discord servers, mostly used by
French-speaking gaming and streaming communities. It is made of
independent modules that server administrators enable and configure from
a web dashboard (https://boteric.fr). The bot works in French and
English.

NEW MEMBER VERIFICATION
When a member joins, the bot posts a verification request in the channel
chosen by the administrator, mentioning the newcomer and telling them
which emoji to react with to obtain the access role. The emoji is drawn
at random among several for each arrival, and the bot also adds a
"reject" emoji. Only the targeted member can trigger the outcome: the
right emoji grants the role, the reject emoji kicks the account. The
request is deleted once handled.

LEVELS AND XP
Members earn XP by taking part in conversations (with a cooldown). The
bot generates a profile card image (avatar, username, level, progress
bar), a server leaderboard and a global leaderboard. Administrators can
attach roles to level thresholds.

MODERATION
Warnings with reason and history, kick, ban, bulk message deletion, and
auto-moderation based on a list of forbidden words defined by each
server. An optional module detects explicit images: attached images are
classified by a model that runs locally on our own server, the message
is deleted and the action configured by the administrator (warn, kick or
ban) is applied and reported in the moderation channel.

AI ASSISTANT
In servers where an administrator enabled it, members can mention the
bot to ask a question and get an answer generated by a language model.

UTILITIES AND FUN
Polls, member and server information, avatars and emojis in full size,
text encoding/decoding, and a few fun commands.

TWITCH
Automatic notification in a Discord channel when a Twitch channel
followed by the server goes live.

2 — SERVER MEMBERS INTENT
========================================================================

--- Why do you need the Guild Members Intent? ---

We need it to receive the GUILD_MEMBER_ADD event, which drives our
member verification module.

When a new member joins a server where the module is enabled, the bot
immediately posts a verification request in the channel configured by
the administrator. The request mentions the newcomer and tells them
which emoji to react with in order to receive the access role. That
emoji is drawn at random for every arrival among several, and the bot
adds a second, "reject" emoji next to it. The bot checks that the
reaction comes from the member the request was created for, in the right
server and channel: the right emoji grants the role, the reject emoji
kicks the account, and the request is then deleted.

This is an anti-automation gate. Because the expected emoji changes on
every arrival, a script that reacts to everything, or that learned a
fixed emoji, hits the reject emoji and is removed. Bots joining the
server are ignored.

Without the Server Members Intent the bot never receives the join event,
so no request is posted and the module does not work at all. There is no
alternative: an interaction-based flow would require the newcomer to
already know about and run a command, in a server where they cannot see
any channel yet.

Member data received through this intent is only used inside the server
where the event happened. The other features that need a member object
(level card, member information, moderation commands) fetch that single
member on demand; we never download or store member lists.

--- Do you store API data off-platform? ---

ANSWER: Yes

Minimal and strictly functional. We store in a MongoDB database hosted
on our own server:
- Discord identifiers (user, server, channel, role and message IDs);
- XP and level counters per user and per server;
- moderation warnings (warned user ID, moderator ID, reason, date);
- pending verification requests (user ID, message ID, expected emoji);
- the configuration chosen by server administrators (prefix, language,
  enabled modules, channels, roles, forbidden words, followed Twitch
  channels);
- for users who log in to the dashboard: their Discord ID, a linked
  Twitch ID if they provide one, their premium status and their custom
  level-card background image (stored on Google Cloud Storage).

We do not store member lists, usernames, avatars, e-mail addresses or
presence data.

A daily backup of the database is uploaded to our Google Cloud Storage
bucket.

Retention: data is not deleted automatically when the bot is removed
from a server. Removals are very often temporary (accidental kick,
maintenance, migration), and automatic deletion would destroy years of
member progression and the whole server configuration with no way back.
This is stated in our privacy policy. Any data is deleted on request from
a server administrator (for their server) or from a user (for their own
data), through our support server or contact@trenderapp.com, within 30
days.

3 — MESSAGE CONTENT INTENT
========================================================================

--- Can users opt out of having their message content data tracked? ---

ANSWER: No

(Individual members cannot opt out. Each feature that reads message
content is off by default and is enabled per server by an administrator;
nothing is tracked or profiled per user.)


--- Do you store message content data off-platform? ---

ANSWER: Yes   [see note A at the bottom before choosing]

Only two narrow cases, both inside a moderation warning record:
- when a moderator issues a sanction with a command, the reason they
  typed after the command is saved as the reason of the warning;
- when auto-moderation triggers, the forbidden word(s) that matched,
  taken from the server's own list, are saved as the reason.
Ordinary messages are never stored: their content is read in memory when
the event is received and then discarded. Nothing is logged.


--- Will message content data be used for machine learning / AI
    training? ---

ANSWER: No

Message content is never used to train, fine-tune or evaluate any model,
by us or by a third party.
For transparency: the optional AI assistant sends the text of a message
that explicitly mentions the bot to the OpenAI API to generate an
immediate reply (inference only). The request is sent with storage
disabled (store: false) and API data is not used by the provider for
training. We keep no copy. The explicit-image detection runs on a
pre-trained model executed locally on our server; images are not sent
to any third party, are not stored, and are not used for training.


--- Why do you need the Message Content Intent? ---

VIDEO: https://boteric.fr/assets/verif/message_intent.mp4
A member writes an ordinary message in a public channel, without
mentioning the bot and without any command. The bot detects a term from
the server's forbidden-word list, records a warning and posts the alert
in the moderation channel, showing the term that matched.

1) AUTO-MODERATION ON FORBIDDEN WORDS (main need)
Each server defines its own list of forbidden words or expressions. When
the module is enabled, the bot compares the text of every message to
that list; on a match it warns the author and notifies the moderation
team in the configured channel.
This cannot be done any other way. Moderation means examining messages
that nobody voluntarily submits to the bot: ordinary messages, with no
mention and no command. Interactions and mentions do not cover them.

2) EXPLICIT IMAGE DETECTION
When the module is enabled, images attached to messages (png/jpg) are
classified by a model running locally on our server. If an image is
classified as explicit, the message is deleted and the action chosen by
the administrator (warn, kick or ban) is applied and reported to the
moderators. Channels can be excluded by the administrator.
Attachments are covered by the same intent as text: without it the bot
sees no image. A slash command is no substitute, as someone posting an
explicit image will not report it themselves.

3) PREFIX COMMANDS (secondary)
The bot historically works with text commands using a prefix that each
server can customise (for example *help, *level, *warn, polls with
quoted options). We know application commands cover this use case, and the
bot already offers some globally (level, stats, image check); we do not
present this as the main justification. The two needs above are the ones no alternative replaces.

In every case processing is ephemeral: content is analysed in memory and
dropped. Auto-moderation and image detection are disabled by default and
must be explicitly enabled by a server administrator.

A. "Store message content off-platform": the previous submission said
   No. Strictly, the reason typed by a moderator after *warn / *kick /
   *ban comes from a message and is saved in the warn collection, and
   the warn-logs channel in both videos shows such reasons. "Yes" with
   the explanation above is the answer that matches the code.

B. Things in the previous French file that did not match the code and
   were corrected here:
   - "personalised welcome message": the join handler only posts the
     verification request, there is no welcome message.
   - explicit-image detection is local (nsfwjs + TensorFlow), not
     OpenAI; and it deletes the message and warns/kicks/bans, it does
     not only alert.
   - backups are uploaded to Google Cloud Storage, not kept on the same
     server.
   - the level system / leaderboard does not need the member list; the
     Members intent is only really needed for the join event.
   - a wrong reaction does not kick: only the reject emoji does.
